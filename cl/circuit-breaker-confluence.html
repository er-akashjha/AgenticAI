1. Executive Summary

📌 TL;DR

Today, when a supplier partially fails (e.g., EPS fails for prepaid but succeeds for postpaid), our system treats the connector as a single unit — causing unnecessary failures across healthy configurations. This RFC proposes adding a configuration-level (and optionally brand/chain-level) circuit breaker inside the USG layer, keyed by supplierId + configurationId [+ brandId]. This isolates partial failures without touching any connector code.

❌ Without this change

  • One failing configuration trips the whole connector
  • Healthy configurations are blocked unnecessarily
  • Brand-specific failures go undetected until they flood logs
  • No automatic recovery — manual intervention required

✅ With this change

  • Each configuration has its own independent CB state
  • Healthy configs continue serving requests unaffected
  • Brand/chain failures are isolated and tracked separately
  • Automatic probe + recovery via HALF-OPEN state

2. The Problem We Are Solving

2.1 Context — How Our Connector System Works

We have a set of supplier connectors written in C# — one per supplier (EPS, HB, Priceline, etc.). Each connector is shared across multiple configurations. For example, the EPS price connector serves:

  • Prepaid configuration — fetches rates for prepaid inventory
  • Postpaid configuration — fetches rates for postpaid inventory

The USG (Unified Search Gateway) layer sits above all connectors, decides which configuration to invoke, and curates the aggregated response.

2.2 Real Failure Patterns We Have Observed

Three distinct failure patterns have been observed in production:

PatternExampleCurrent Impact
Config-level failure EPS prepaid times out; postpaid is healthy All EPS traffic slows — postpaid unnecessarily delayed
Brand/chain failure EPS prepaid fails for Hilton chain only Hilton errors mix with healthy responses — hard to isolate
Full supplier failure EPS is completely down All configs fail — handled partially today
⚠️ Key Insight

Patterns 1 and 2 are the most common in practice and the least handled. A supplier can be partially healthy — and our current architecture has no mechanism to leverage that.

3. Current State

Today's failure handling (if any) is coarse-grained:

  • Circuit breakers (if implemented) are at the connector level — one state per supplier
  • There is no mechanism to distinguish which configuration is failing within a supplier
  • There is no mechanism to detect brand or chain specific degradation
  • Recovery is manual — no automatic probing once a supplier is marked as failed

4. Proposed Solution — Granular Circuit Breakers in USG

4.1 Why USG Is the Right Layer

The USG layer is uniquely positioned because it already knows — before making any connector call — the exact supplier + configuration + brand/chain context of each request. This makes it the ideal enforcement point for circuit breakers. Adding CBs here means:

  • Zero changes to any connector code
  • A single, consistent policy enforced across all suppliers
  • One place to monitor, alert on, and tune CB behavior

5. The CB Key Design

This is the most critical design decision. Each circuit breaker is identified by a composite key: 

CB_KEY = {supplierId}:{configurationId}[:{brandOrChainId}]

Example Keys

CB KeyWhat It GuardsGranularity
eps:prepaidEPS prepaid configuration globallyConfig-level
eps:postpaidEPS postpaid configuration globallyConfig-level
hb:prepaidHB prepaid configuration globallyConfig-level
eps:prepaid:hiltonEPS prepaid, Hilton chain onlyBrand/chain-level
eps:prepaid:marriottEPS prepaid, Marriott chain onlyBrand/chain-level
priceline:postpaid:accorPriceline postpaid, Accor chain onlyBrand/chain-level
💡 Key Design Principle

Brand/chain keys are additive and layered. USG checks from most-specific to least-specific. If eps:prepaid:hilton is OPEN, the call is blocked — even if eps:prepaid is healthy. This means you get fine-grained protection without duplicating logic.

6. Circuit Breaker State Machine

Each CB key tracks one of three states:

StateBehaviorTransition
CLOSED Normal operation. All requests flow through to the connector. → OPEN when failure rate exceeds threshold in window
OPEN Failing. USG returns fallback immediately. Connector is NOT called. → HALF-OPEN after cooldown period (e.g., 30s)
HALF-OPEN Probe mode. One test request is allowed through to check recovery. → CLOSED on success · → OPEN on failure

6.1 Recommended Thresholds (Starting Point)

ParameterRecommended ValueNotes
Window typeSliding time windowMore accurate than count-based windows
Window duration60 secondsTune per supplier SLA
Failure rate threshold50%Use rate, not absolute count
Minimum requests in window10Avoid tripping on low-traffic configs
Cooldown (OPEN → HALF-OPEN)30 secondsStart conservative, can reduce later
⚠️ Use failure rate, not absolute count

An absolute error count of 5 means very different things at 10 req/min vs 10,000 req/min. A percentage threshold on a sliding window is far more reliable across different configuration traffic volumes.

7. USG Resolution Logic — Step by Step

  1. Extract context from incoming request: supplierId, configurationId, brandId (if present)
  2. Build CB keys: brand-level key (eps:prepaid:hilton) and config-level key (eps:prepaid)
  3. Check brand-level CB key → if OPEN: return fallback immediately (skip steps 4–6)
  4. Check config-level CB key → if OPEN: return fallback immediately (skip steps 5–6)
  5. Dispatch to connector → execute the actual supplier call
  6. Record outcome (success or failure) against both the brand-level and config-level keys
  7. Return response to caller, including a metadata flag if a fallback was used

7.1 Pseudocode

// USG dispatch method (simplified)
public async Task<SupplierResponse> Dispatch(SearchRequest request)
{
    var configKey = $"{request.SupplierId}:{request.ConfigId}";
    var brandKey  = $"{configKey}:{request.BrandId}"; // null if no brand

    // Check most-specific → least-specific
    if (brandKey != null && circuitBreakerRegistry.IsOpen(brandKey))
        return FallbackResponse("brand_circuit_open", brandKey);

    if (circuitBreakerRegistry.IsOpen(configKey))
        return FallbackResponse("config_circuit_open", configKey);

    try
    {
        var response = await connector.Execute(request);
        circuitBreakerRegistry.RecordSuccess(configKey);
        if (brandKey != null) circuitBreakerRegistry.RecordSuccess(brandKey);
        return response;
    }
    catch (SupplierException ex)
    {
        circuitBreakerRegistry.RecordFailure(configKey);
        if (brandKey != null) circuitBreakerRegistry.RecordFailure(brandKey);
        throw;
    }
}

8. Brand / Chain Granularity

8.1 When to Use Brand-Level CBs

Brand/chain-level circuit breakers are most valuable when a supplier returns data per-brand and some brands are systematically failing (e.g., incorrect mapping, missing inventory, API-side data issue for that chain).

8.2 Extraction Strategy

Brand context must be available before the call is dispatched. Two approaches:

ApproachWhen to UseTrade-off
Request-time extraction Brand is part of the search request payload ✅ Cheapest — no extra work. Most common case.
Response-tagging Brand only known after parsing supplier response ⚠️ More complex — must tag failures post-response with brand ID
📋 Recommendation

Start with config-level CBs only. Add brand/chain-level CBs only after you observe recurring brand-specific degradation patterns in production. This keeps the initial implementation simple and lets you validate the core mechanism first.

9. Fallback Strategy

When a CB is OPEN, USG should not simply return an error. The following fallback hierarchy is recommended:

PriorityFallbackWhen to Use
1Cached / stale ratesIf rate data has acceptable TTL for the use case
2Alternate supplier redirectIf USG has a configured fallback supplier for that config
3Graceful empty resultReturn empty with metadata: source: "circuit_breaker_fallback"
✅ Always include fallback metadata

Tag all fallback responses with a structured metadata field (e.g., cbKey, cbState, fallbackType). This allows downstream systems and monitoring tools to distinguish CB-triggered responses from real supplier responses.

10. Implementation Guidance

10.1 Recommended Stack

ConcernRecommendationRationale
CB libraryPolly v8 (C#)Native .NET, supports keyed CBs, well-maintained
CB state storageRedisShared across USG instances; TTL-based sliding windows built-in
Key formatcb:{supplier}:{config}[:{brand}]Namespaced to avoid Redis key collisions
ObservabilityCustom metrics + existing APMCounter per CB key, state transition events

10.2 Redis Key Example

// Redis hash per CB key
cb:eps:prepaid         → { state: "OPEN",   failureRate: 0.63, windowStart: ... }
cb:eps:postpaid        → { state: "CLOSED", failureRate: 0.04, windowStart: ... }
cb:eps:prepaid:hilton  → { state: "HALF_OPEN", lastProbe: ... }

10.3 Metrics to Expose

  • cb.state_transitions — count of CLOSED→OPEN, OPEN→HALF-OPEN, HALF-OPEN→CLOSED transitions, tagged by CB key
  • cb.fallback_served — count of requests served from fallback, tagged by CB key and fallback type
  • cb.failure_rate — current failure rate per CB key (gauge)
  • cb.open_duration_seconds — how long each CB key has been OPEN

10.4 Phased Rollout

PhaseScopeGoal
Phase 1Config-level CBs for one supplier (EPS)Validate mechanism, tune thresholds
Phase 2Config-level CBs for all suppliersBroad coverage, monitor for edge cases
Phase 3Brand/chain-level CBs for high-volume brandsFine-grained isolation where needed

11. Decision Matrix

QuestionDecision
Where should CBs live?USG layer — owns routing, single enforcement point
CB granularity level?Config-level (mandatory) + Brand/chain-level (additive, optional)
Window type?Sliding time window (60s) + failure rate threshold (50%)
State storage?Redis — shared across all USG instances
CB library?Polly v8 (C#) with Redis-backed distributed state
Should connectors be modified?No — USG fully owns this, connectors stay unchanged
Should brand-level CBs be in Phase 1?No — start with config-level, add brand-level after validation

12. Open Questions for Architects

🔍 Items requiring team input

Please add comments / decisions inline in Confluence.

  1. Threshold values — Are 50% failure rate and 60s window appropriate for our SLAs, or should they be supplier-specific?
  2. Redis availability — Do we have a Redis cluster already in USG's infrastructure, or does this require provisioning?
  3. Fallback precedence — Should stale cache always take priority over alternate supplier redirect? Who owns this decision per configuration?
  4. Manual override — Do we need an admin API to manually OPEN or CLOSE a CB key (e.g., for planned supplier maintenance)?
  5. Brand identity — Is brandId / chainId consistently available in all search request payloads today, or does it require enrichment?
  6. Alerting — When a CB transitions to OPEN, who is notified? What is the escalation path for supplier degradation?
